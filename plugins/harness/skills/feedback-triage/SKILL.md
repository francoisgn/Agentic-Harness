# Trier des retours de test

Références : `.harness/docs/METHODOLOGY.md` §3–§4 (sinon `${CLAUDE_PLUGIN_ROOT}/docs/METHODOLOGY.md`), taxonomie
`.harness/labels.json` + `.github/labels.local.json`.

1. **Découper** les retours en points atomiques (un comportement, un écran, une attente). Donner à chacun une
   référence courte `[Préfixe + n]` (préfixe : $ARGUMENTS, ou l'initiale de l'onglet / de la zone).
2. **Doublons** : pour chaque point, chercher les issues ouvertes et fermées (titres, corps, synonymes). Un doublon →
   commenter l'issue existante avec le nouveau cas au lieu d'en créer une ; une issue fermée qui revient → la rouvrir
   ou en ouvrir une liée, selon le projet.
3. **Labels** de chaque point : un type, l'onglet / la zone si le projet en a, une priorité (`P1 🔴` faux ou bloquant,
   `P2 🟠`, `P3 🟢`), un modèle (`haiku` local et spécifié, `sonnet` plusieurs fichiers / état, `opus` moteur, règles,
   architecture), une taille (S / M / L). `à clarifier` si une décision produit manque (dire laquelle dans l'issue).
   Un label absent des fichiers de labels → l'ajouter au fichier d'abord.
4. **Montrer le plan à l'opérateur avant de créer** (tableau : réf, point, labels, doublon éventuel) : créer des issues
   est visible de tous.
5. Après accord : créer l'**issue parapluie** (`feedback` + priorité la plus haute de ses points), titre
   `Retours <date ou version>`, avec le tableau `| Réf | Point | Lot | Issue | PR |` ; puis **une issue par point**, titre
   `[Réf] Onglet : sujet`, corps : `### Résumé`, constat, attendu, captures, sources ; la rattacher comme sous-issue du
   parapluie ; reporter son numéro dans le tableau.
6. Proposer un regroupement en **lots** (issues qui touchent les mêmes fichiers ou le même modèle) et remplir la colonne
   Lot. Tout commentaire finit par le pied `---` / `_Generated by [Claude Code](https://claude.ai/code)_`.
